Concepts

How OntoRAG thinks

The ideas the pipeline, the specifications and the tools are built on. Each links to where it is defined precisely.

The ontology is the contract

In OntoRAG, the ontology is not a by-product of retrieval. It is the agreement between people, the pipeline and agents about what can be said. Classes and properties define what the graph may contain. Extraction may only produce instances of approved terms, and agents query through tools derived from the same schema. When something is missing, the result is a proposal to extend the schema, not an invented field.

Baselines first

A new schema starts from existing baseline ontologies: a domain schema (for role-playing games, rpg-schema) plus general vocabularies such as schema.org, FOAF and Dublin Core. After a language model proposes terms from the documents, an alignment step decides for each term whether to:

Reuse
use the baseline term as it is;
Extend
add a new term declared as a sub-class or sub-property of a baseline term;
Induce
add a genuinely new term, with a rationale.

Every term keeps its origin, so the finished ontology shows what came from which standard. Baselines are served by an ontology catalog. Terms: orag:BaselineOntology, orag:alignment.

The schema card

The schema lives in a schema card, a JSON document that lists classes, datatype and object properties, events and aliases, each with its origin. Language models only ever produce proposals. The next card comes from a deterministic merge: names are normalised, the longer description wins and baseline origins are preserved. The same inputs therefore always give the same card, and a diff between two cards is exactly what changed. The approved card is exported as OWL/RDFS.

Governance

Every artifact has a status: proposed, approved, deprecated or revoked. A person reviews each proposed card and can flip reuse, extend or new, rename or drop terms. Only approved cards drive extraction. When datasets are stored in git, every approval is a commit, so the history of the schema is its audit trail. Agents default to read-only tools, and anything they write is a proposal. Terms: orag:status.

Every fact has a source

Instances are extracted chunk by chunk, and each carries mentions: the file it came from, the quoted passage, the section path and, for paginated sources, both the physical page and the printed page number a reader would cite. A resource also records which sources attest it and which one defines it. Citations are therefore specific, like "System Reference Document 5.2.1, p. 131, Spells › Spell Descriptions › Fireball", rather than a vague pointer to a chunk. Defined by the provenance ontology.

The repository is the database

A finished dataset is a directory, normally a git repository. It holds the graph (world.ttl), a flat entity index, text chunks and embeddings, all described by a manifest.json. Services read it in place, straight from GitHub, with no database to run and no clone. Versioning, review, access control and hosting come from git. Defined by the dataset format.

Packs and composition

A dataset built from many sources decomposes into packs, one per source, plus a shared spine of vocabulary. A pack holds what its source says: its statements in a named graph, its chunks and its vectors. Packs declare dependencies, such as a supplement requiring its core rules. Selecting packs selects a world, which serves two purposes:

Access scope
a consumer sees the packs it holds plus the spine, and nothing else. Holding a supplement does not grant its core book.
Composition
for building or evaluating a coherent world, the selected packs are closed over their dependencies.

Whoever serves the data enforces the access scope: an application maps what a user owns to packs and passes that set to retrieval. Rules: packs and composition.

Retrieval through the ontology

Because chunks are linked to the entities they mention, retrieval can go through the graph instead of only through vector similarity. ontorag-mcp offers three modes: ontology (entity matching plus keyword fallback, no embeddings), vector (dense similarity), and hybrid (sparse candidates re-ranked densely). In its evaluation on the Ars Magica dataset (v0.6.0, 320 questions across all 25 books), recall@1 was:

Question typeOntologyHybridVector
Names an entity0.990.820.42
Needle in a haystack0.970.750.28
Paraphrase0.650.490.48

The correct answers come from the dataset's own entity links, so these numbers measure retrieval through a graph against the graph that built them; the evaluation notes discuss what that does and does not show. Agents then answer with ontology facts and the cited passages together.

Tools for agents

OntoRAG exposes the graph through the Model Context Protocol. Tools are narrow and read-only by default: search, entity lookup, the passages that mention an entity, class listings and guarded SPARQL. A model plans with the schema and retrieves through the graph, instead of reading a pile of paragraphs.
